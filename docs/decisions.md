# CareerMatch 设计决策

记录影响较大的设计决策：当时的背景、做了什么决定、为什么、付出了什么代价。
数字出自 [evals.md](evals.md)。

## 匹配分在代码里计算

- **背景**：v1 让 LLM 按四个子分自己算加权总分。
- **决定**：LLM 只给子分，总分由 `app/services/scoring.py` 按权重计算，
  四舍五入。
- **理由**：评测里 v1 有 62% 的结果算错 1 到 2 分；改后错误为 0。
- **代价**：权重是固定的，不能让模型根据岗位灵活调整。

## 用 LangGraph 状态图编排匹配分析

- **背景**：v2 是两条链顺序调用，规则判断只能硬塞进链里。
- **决定**：v3 用 StateGraph：规则筛选节点、条件路由、节点级 RetryPolicy。
- **理由**：技术栈不符的岗位直接跳过建议生成，省一次 LLM 调用，
  成本比 v2 低约 26%；重试只针对结构化输出失败。
- **代价**：规则节点本身也会出错，评测发现过把多选一要求误判为硬要求，
  已修复并加了测试。

## 技能归并用封闭词表

- **背景**：同一个技能缺口，模型会用不同说法描述，直接计数会拆成好几条。
- **决定**：一次 LLM 调用把每条缺失技能映射到固定词表，统计和分类在代码里做，
  并校验映射没有遗漏、重复或越界。
- **理由**：「从词表里选」比自由生成稳定，统计结果可复现。
- **代价**：词表外的技能只能归到「其他」，词表需要手动维护。

## Vercel 上批量分析同步执行

- **背景**：最初用 FastAPI 的 BackgroundTasks，响应返回后继续跑。
- **决定**：在请求内同步跑完，保留任务记录和轮询接口。
- **理由**：Serverless 函数返回后进程随时可能被回收；15 个岗位约 35 秒，
  远低于 300 秒的函数上限。
- **代价**：岗位数量大幅增加后可能超时，到时需要换成队列。

## AI 助手用 LangGraph 原生的记忆和确认

- **背景**：原来的助手无状态，历史由前端传入，也不能写数据。
- **决定**：checkpointer 按 thread_id 持久化对话；写操作由
  HumanInTheLoopMiddleware 中断，确认后恢复；长期偏好用 LangMem 存进 Store，
  保存前也要确认。
- **理由**：写操作先确认从 0/8 到 8/8；偏好记忆题从 0/3 到 3/3；
  刷新页面可恢复对话。
- **代价**：多了两个依赖和一批不归 Alembic 管的表；
  对话中有待确认的操作时不能发新消息。

## 线上检索只用 BM25，向量融合留作可选

- **背景**：原来的搜索是子串匹配，不搜城市，也给不出总数。
- **决定**：线上默认用 jieba 分词加 BM25。bge-m3 向量和 RRF 融合也已实现：
  向量存普通 JSON 列，在 Python 里算相似度，设 `SEARCH_MODE=hybrid` 开启。
- **理由**：20 个查询上 BM25 的 recall@5 是 0.963，子串匹配 0.722，
  混合 0.943，向量单独 0.792。JD 片段措辞相近，向量区分度不够，
  融合后反而挤掉了 BM25 找到的岗位。保留向量是因为入库时顺带计算、成本很低，
  查询用词和 JD 差异变大时可以直接切换再评测。
- **代价**：同义词、口语化的查询 BM25 可能找不到；评测查询的用词偏向
  JD 原文，对 BM25 有利。岗位规模变大后向量要换 pgvector。

## 评测先行，裁判也要校验

- **背景**：很多指标只能由 LLM 当裁判。
- **决定**：每个裁判都要求先摘录原文依据再下结论，代码检查依据和结论
  是否自相矛盾；维护一份裁判校验集，改了裁判先过校验集，再抽查真实结果。
- **理由**：差距裁判的第一版把加分项当成「JD 没要求」，13 条凭空差距里
  9 条是误判；相关性裁判出现过理由写着不相关、却把岗位标为相关。
  不抽查就会写进错误的结论。
- **代价**：每次评测都要花时间抽查，裁判调用也有成本。
