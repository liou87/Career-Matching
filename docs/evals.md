# CareerMatch 评测

CareerMatch 的质量用两套数据衡量：

- **离线评测**：在固定评测集上跑匹配分析的各个版本，对比准确性、稳定性、
  成本和耗时。改动 prompt、模型或流程前后都跑一次，用数字判断改动是否有效。
- **线上指标**：每次 LLM 调用写一条记录，`/api/metrics` 统计真实使用中的
  成功率、耗时分位数和成本。

## 运行 CareerMatch 离线评测

在 `backend/` 下运行：

```bash
python -m evals.run                                       # v1/v2/v3 各跑 3 遍，带编造检测
python -m evals.run --versions v3 --runs 1 --jobs 3 --no-judge   # 快速冒烟
python -m evals.run --langsmith                           # 同时作为实验上传到 LangSmith
python -m evals.calibrate_judges                          # 改了裁判之后先跑裁判校验集
python -m evals.rescore evals/results/eval_<时间>.json --judge   # 只重跑裁判
python -m evals.agent_eval                                # AI 助手的 35 道题
python -m evals.retrieval_eval                            # 岗位检索的 20 个查询
python -m evals.interview_eval                            # 15 个岗位的面试题
```

结果写到 `evals/results/eval_<时间>.json`（全部原始记录）和同名 `.md`
（汇总表）。完整跑一次三个版本约 5 分钟，花费约 0.5 美元，
其中裁判约 0.25 美元。

评测会调用真实 LLM、产生费用，所以不随 CI 自动运行。GitHub Actions 里的
**Eval** workflow 可以手动触发，需要先在仓库 Secrets 里配置 `DEEPSEEK_API_KEY`。

评测期间不写线上指标表；不加 `--langsmith` 时也会关掉链路追踪，
避免评测流量混进线上数据。

## CareerMatch 评测集

评测集在 `backend/evals/dataset/`，由 `python -m evals.export_dataset`
从本地库导出：

- `jobs.json`：15 个真实岗位的结构化字段，与线上分析时传给模型的字段一致。
- `profile.json`：脱敏画像。仓库公开，姓名、学校、公司名换成占位符，
  技能、项目、学历层次和求职意向保留。
- `labels.json`：差距标注，每个岗位标出候选人真正缺的技能及其常见说法。

> [!IMPORTANT]
> `labels.json` 目前是规则生成的草稿，15 个岗位都还没有人工校对
> （`reviewed: false`），所以基于标注的召回率暂时为空。
> 差距识别的准确率改由裁判自动检查，不依赖标注。校对方法见文末。

## CareerMatch 评测指标

- **成功率**：分析成功返回的比例。
- **耗时 P50 / P95**：单次分析的端到端耗时，只统计成功的。
- **token 与成本**：一次分析里所有 LLM 调用的 token 之和。成本按
  `app/core/config.py` 的价格表估算，取 DeepSeek 官方高峰时段价格，偏保守。
- **分数算错次数**：`match_score` 与四个子分按权重算出的值不一致的次数。
- **空泛建议**：行动建议命中「系统学习」「刷LeetCode」等短语的条数，
  口径与 v1→v3 的历史评测一致。
- **稳定性**：同一岗位跑 3 遍，看分数的标准差、最大极差和完全一致的比例。
- **差距检查（裁判）**：对模型给出的每条缺失技能，裁判先摘录 JD 里对应的
  原文，再分成三类：有效（JD 有要求且画像确实缺）、凭空差距（JD 三处都找不到）、
  误报缺失（画像已具备，或 JD 是多选一且画像已满足）。有效率就是不依赖人工
  标注的准确率。摘录到原文却判凭空差距视为自相矛盾，按有效计并标记。
- **差距识别召回率（人工标注）**：模型给出的缺失技能与人工标注比对，
  任一别名出现在任一条预测里（不区分大小写）就算识别到。
- **编造率**：用更强的 `deepseek-v4-pro` 当裁判，逐条检查建议有没有把画像里
  不存在的经历、项目、技能说成候选人已有的。「建议去做」不算编造。

裁判本身的可靠性见下文「校验 CareerMatch 的裁判」。

## CareerMatch 各版本对比

2026-10-09，模型 `deepseek-flash`，15 个岗位 × 3 次，
原始记录见 `evals/results/eval_20261009_2137.json`。

| 指标                        | v1 单 prompt | v2 两步链 | v3 LangGraph |
| --------------------------- | ------------ | --------- | ------------ |
| 成功率                      | 100%         | 100%      | 100%         |
| 耗时 P50                    | 6.3s         | 10.6s     | 10.0s        |
| 单次成本（美元）            | 0.0016       | 0.0027    | 0.0020       |
| 分数算错                    | 28 / 45      | 0 / 45    | 0 / 45       |
| 空泛建议                    | 6 / 135      | 0 / 135   | 0 / 81       |
| 分数标准差                  | 0.46         | 0.55      | 0.41         |
| 3 次分数完全一致的岗位比例  | 53%          | 60%       | 80%          |
| 差距有效率                  | 96.2%        | 95.3%     | 94.0%        |
| 凭空差距                    | 0%           | 2.3%      | 2.3%         |
| 误报缺失                    | 3.8%         | 2.3%      | 3.8%         |
| 编造率                      | 0%           | 0%        | 0%           |

- **让 LLM 自己做加权求和不可靠**：v1 有 62% 的结果分数算错，偏差 1 到 2 分。
  v2 起改为代码里按子分加权，错误归零。
- **拆成两步后建议质量更好**：v1 有 6 条空泛建议，v2、v3 为 0。
- **v3 比 v2 便宜约 26%**：技术栈不符的岗位由规则节点直接跳过建议生成，
  省掉一次 LLM 调用。
- **temperature 为 0 仍有波动**：同一岗位多次分析，分数最大相差 9 分。
- **差距识别整体可靠**：三个版本的有效率都在 94% 以上。v1 略高，但每个岗位
  平均只列 7 条缺失技能，v3 列 8.9 条，有没有漏掉真实差距要靠召回率判断。
- **剩下的差距错误主要是误读多选一**：JD 写 `Python/Java/Scala`、画像已有
  Python，模型仍列出「Java/Scala」。这和下文规则筛选的问题同源，
  下一步可以在分析 prompt 里专门约束。
- **编造率在当前评测集上没有区分度**：三个版本都是 0。这个指标保留下来，
  用于后续加自检节点、换模型时做回归检测。

## 评测驱动的修复：规则筛选误排除

上面的结果里，v3 只给 15 个岗位中的 9 个生成了建议。排查发现规则筛选只要
在必需技能里看到 Java 或 Golang 就排除岗位，但其中两条要求其实是多选一：
`Python/Java/Scala` 和 `至少一种编程语言（如Java、Python等）`。
被误排除的恰好是「大模型应用开发工程师」和「AI应用开发工程师」两个目标岗位，
它们完全拿不到提升建议。

修复：命中排除语言的那条要求里，如果同时列了候选人已有的技能，视为多选一，
不排除；技能按完整单词比对，避免 `SQL` 命中 `MySQL`。真实 JD 里的这几种
写法都加进了单元测试。修复后重跑 v3（`eval_20261009_2140.json`）：

| 指标                  | 修复前 | 修复后  |
| --------------------- | ------ | ------- |
| 被排除的岗位          | 6      | 4       |
| 其中误排除            | 2      | 0       |
| 单次成本（美元）      | 0.0020 | 0.0023  |
| 空泛建议              | 0 / 81 | 0 / 99  |
| 差距有效率            | 94.0%  | 94.9%   |
| 编造率                | 0%     | 0%      |

成本上升约 13%，是因为多给两个岗位生成了建议，属于预期内的代价。

## 校验 CareerMatch 的裁判

裁判也是 LLM，它给出的数字在用之前要先验证。差距检查的第一版判断规则在真实
数据上出过问题：抽查 v3 被判为「凭空差距」的 13 条，对照 JD 原文后发现
9 条是裁判判错，主要是把加分项、写在职责里的要求、比 JD 说得更细的差距
当成了 JD 没要求。这一版给出的凭空差距约 10%，明显高估。

改进后的规则做了三处调整：要求先摘录 JD 原文再分类；明确加分项、职责、
细化说法都算有效，多选一已满足算误报；加上自相矛盾时的一致性约束。

`evals/calibrate_judges.py` 把这些误判类型做成了 15 条固定样本，
大部分用真实 JD 里的原话：

| 裁判版本   | 差距检查 | 编造检测 | 回答依据 |
| ---------- | -------- | -------- | -------- |
| 第一版规则 | 10 / 12  | 3 / 3    | -        |
| 当前规则   | 12 / 12  | 3 / 3    | 7 / 7    |

改进后重新评估真实数据，一致性约束没有触发过，数字全部来自裁判自己的判断。
v3 剩下的 2 条凭空差距和 5 条误报缺失都逐条核对过 JD 原文，判断正确。
第一版在校验集里加分项样本全部判对，却在真实数据的长列表里判错，
所以校验集只是第一道关，换裁判或改规则后仍要抽查真实结果。

## 多选一约束对 CareerMatch 差距识别的影响

上面的差距检查发现，剩下的错误主要是模型把多选一要求里的其他选项列为缺失。
v3 的分析 prompt 加了一条约束：JD 里多选一的要求满足任意一项就算满足。
v2 的 prompt 冻结不动，保证历史对比可以复现。重跑 v3
（`eval_20261010_2038.json`，与修复规则筛选后的 v3 对比）：

| 指标                 | 加约束前 | 加约束后 |
| -------------------- | -------- | -------- |
| 差距有效率           | 94.9%    | 99.2%    |
| 误报缺失             | 3.6%     | 0.8%     |
| 凭空差距             | 1.4%     | 0%       |
| 每次列出的缺失技能   | 9.0 条   | 8.2 条   |
| 单次成本（美元）     | 0.0023   | 0.0022   |

列出的条数少了约 9%，主要集中在有多选一要求的 5 个岗位（平均少 1.7 条，
其余岗位少 0.3 条）。抽查减少最多的两个岗位，去掉的大多是多选一选项和
JD 没要求的条目，但也有个别 JD 写明的要求（如岗位 3 的「技能封装」）
这次没有列出。准确率的提升是确定的，召回率有没有损失要等人工标注后才能确认。

## 评测 CareerMatch 的 AI 助手

35 道题（30 道单轮、5 道多轮）覆盖画像查询、岗位搜索、技能排行、单岗分析、
写操作、偏好记忆、闲聊和超出范围。题目和预期在
`evals/dataset/agent_cases.json`。每道题检查：

- **工具和参数**：该调用的工具有没有调用、关键参数（如 `job_id`）对不对。
  多轮题看所有轮次，前一轮查过的信息后一轮直接用是合理的。
- **写操作先确认**：写数据的题必须停在确认这一步，不能直接执行；
  只读的题不能出现确认中断。
- **必须内容**：回答里有没有出现关键信息，如正确的匹配分。
- **回答依据**：裁判逐条检查回答里关于用户数据的说法能不能在工具返回、
  已保存的偏好或此前的对话里找到原文。

评测在独立的临时数据库里进行，种子数据来自评测集，不碰真实数据。
改造前后用同一版裁判评判（`agent_eval_stateless_20261009_2337.json`、
`agent_eval_agent_20261010_2037.json`）：

| 指标             | 改造前（无状态） | 改造后  |
| ---------------- | ---------------- | ------- |
| 通过率           | 22 / 35          | 30 / 35 |
| 写操作先确认     | 0 / 8            | 8 / 8   |
| 偏好记忆         | 0 / 3            | 3 / 3   |
| 参数准确率       | 77.8%            | 100%    |
| 无依据说法       | 4 / 220          | 3 / 202 |
| 单轮耗时 P50     | 2.4s             | 2.0s    |
| 每题成本（美元） | 0.00057          | 0.00058 |

- 改造前没有写操作和记忆，相关题目只能如实回答「做不到」，没有编造操作结果。
- 迭代中发现：询问已保存的偏好时，助手会误调保存偏好的工具（被确认机制拦下，
  没有写入）。在系统提示里明确调用时机后修复。
- 回答依据在改造前后处于同一水平；剩下的错误包括把岗位名里的错字「上程帅」
  擅自改成「工程师」、合并两项排行后数字算错。
- 仍未通过的两道题暴露了工具能力缺口：搜索不支持按城市筛选、无法统计岗位总数，
  另有「匹配分最高的岗位」需要逐个查分析。这些放到第四阶段与检索重设计一起做。

AI 助手的回答依据裁判同样经过校验，并迭代了三次：把用户本轮消息算作依据、
允许有完整列表支撑的「没有某项」说法、排除助手对自身能力和系统限制的描述。
每次调整后先过校验集，再重新评判基线和新版，保证两边口径一致。

## 评测 CareerMatch 的岗位检索

20 个查询（`evals/dataset/retrieval_queries.json`），对比四种方式的排序质量：
第四阶段之前的子串匹配、jieba 分词加 BM25、bge-m3 向量、两路用 RRF 融合。
子串匹配的输入用助手当时会传的关键词（如 `RAG`），这是对旧方式最有利的设定。

标注分两类：

- **规则推导**（14 个）：按城市、公司、技能、标题出题，相关岗位直接从数据算出。
- **语义查询**（6 个）：如「偏服务端工程、需要高并发或分布式经验的岗位」，
  由裁判对全部岗位逐一判断，结果缓存在 `evals/dataset/retrieval_labels.json`。
  抽查时发现裁判第一版只输出「相关岗位列表」，出现过理由写着不相关、
  却把岗位放进列表的情况；改成对每个岗位先写依据再下结论后重新标注，
  28 条相关标注逐条核对，都能在岗位原文里找到依据。

指标：recall@5（前 5 条找回的相关岗位比例，相关岗位超过 5 个时以 5 为分母）、
MRR（第一个相关岗位名次的倒数）、首位命中率。
结果（`retrieval_eval_20261011_0037.json`）：

| 方式       | recall@5 | 规则查询 | 语义查询 | MRR   | 首位命中 |
| ---------- | -------- | -------- | -------- | ----- | -------- |
| 子串匹配   | 0.722    | 0.767    | 0.617    | 0.875 | 85%      |
| BM25       | 0.963    | 0.962    | 0.967    | 1.0   | 100%     |
| 向量、混合 | 待测     | 待测     | 待测     | 待测  | 待测     |

> [!NOTE]
> 向量和混合检索的代码已经就绪，需要配置 `SILICONFLOW_API_KEY` 后才能评测。
> 这批语义查询里的词（如「评测」「多 Agent」）在 JD 原文中本来就出现过，
> BM25 已经表现很好，向量能带来多少额外收益要等实测。

## 第四阶段对 CareerMatch AI 助手的影响

`search_jobs` 改为混合检索，支持按城市、公司筛选，返回筛选后的岗位总数、
与查询相关的岗位数和命中的片段原文；新增 `list_job_scores`，
汇总所有岗位的匹配分。
三次评测用同一套设计（`agent_eval_agent_20261010_2037.json`、`..._0042.json`、
`..._0044.json`）：

| 指标           | 第三阶段结束 | 新工具上线 | 区分总数和相关数 |
| -------------- | ------------ | ---------- | ---------------- |
| 通过率         | 30 / 35      | 31 / 35    | 34 / 35          |
| 必须内容命中率 | 90.9%        | 100%       | 100%             |
| 回答依据率     | 90.3%        | 87.1%      | 96.8%            |
| 无依据说法     | 3 / 202      | 4 / 225    | 2 / 242          |

- 第三阶段暴露的三个能力缺口（按城市找岗位、统计总数、找匹配分最高的岗位）
  都已补上，对应题目全部通过。
- 新工具上线后，助手会用 `list_job_scores` 直接拿匹配分，原来要求必须调用
  `get_job_analysis` 的三道「只问匹配分」的题改为两条路径都算对，分数仍由
  必须内容检查把关。评测框架给裁判看的工具输出原来截断在 3000 字符，
  搜索结果变长后裁判看不全，已放宽到 10000 字符。
- 第二次迭代修了一个工具设计问题：最初只返回筛选后的总数，不带筛选时永远是 15，
  助手会把它误当成相关岗位数。增加单独的 `matched` 后，这类错误消失。
  同时要求助手以片段内容判断相关性，不对弱相关的结果做推断。
- 每道题只跑一次，通过率有随机波动；后两次之间只改了这两处，
  提升基本可以归因到它们。
  剩下的一条错误是助手把加分技能里有 RAG 的岗位归为「片段里没有体现 RAG」。

## 评测 CareerMatch 的面试题

面试题从 JD 的要求出发，用匹配分析的优势和差距排优先级，每题先原样摘录它考察的
JD 要求。对评测集 15 个岗位各生成一套（`interview_eval_20261011_0102.json`）：

| 指标                 | 结果                 |
| -------------------- | -------------------- |
| JD 依据率            | 97.3%                |
| 必需技能覆盖率       | 67.4%                |
| 通用题比例           | 0%                   |
| 优势和差距都有的岗位 | 15 / 15              |
| 答题要点编造率       | 0%（596 条）         |
| 每岗位成本 / 耗时    | 0.0034 美元 / 约 14s |

- 除编造率由已校验的裁判判断外，其余都是规则计算。
- JD 依据率按逐字比对计算。4 道未通过的题抽查后都对应 JD 原文：
  有的在摘录后加了「（加分项）」之类的注释，有一处把 JD 原文的错字「要盖」
  改成了「覆盖」，按含义算接近 100%。
- 覆盖率是有意的取舍：每套 6 到 10 道题优先给差距和核心职责，
  未覆盖的多是候选人已熟练的基础项，如 Python、Prompt Engineering。

## 与 2026 年 7 月历史数据的关系

README 早期的 v1→v3 对比（v1 算错 7/15 等）是 7 月在 `deepseek-chat`
上用旧脚本跑的。`deepseek-chat` 已是弃用别名，现在实际由 `deepseek-flash`
响应。本文数据换了模型、画像改为脱敏版本、每个岗位跑 3 遍，
两批数字不能直接比较，结论方向一致。旧脚本（`evals/*_eval.py`）保留，
用于复现当时的结果。

返回总体和按角色（analysis、suggest、jd_parse、agent 等）分组的调用次数、
成功率、耗时 P50/P95、平均 token 和估算成本，以及平均单次匹配分析成本。
数据来自 `llm_calls` 表，每次 LLM 调用写一条，写入失败不影响请求本身。

## CareerMatch 评测的已知局限

- 评测集只有 15 个岗位、一份画像，结论适合版本间相对比较，不代表通用水平。
- 编造率和差距检查依赖 LLM 裁判，可能有误判；校验集只有 15 条样本。
- 成本按高峰价估算，DeepSeek 非高峰时段半价，实际花费更低。

## 校对 CareerMatch 差距标注

1. 打开 `backend/evals/dataset/labels.json`，每个岗位的 `missing` 是规则草稿：
   JD 必需技能里画像没覆盖的项。规则很粗，比如会把画像已有的
   「DeepSeek API」对应的「LLM API」误判为缺失。
2. 对照 `jd_required` 和画像，删掉不算缺失的、补上漏掉的。
   `aliases` 写上模型可能用到的说法，例如 `["RAG", "检索增强"]`。
3. 改完一个岗位就把它的 `reviewed` 改成 `true`，只有校对过的岗位参与计算。
4. 不用重跑 LLM，直接用已有结果重新计算：

   ```bash
   python -m evals.rescore evals/results/eval_20261009_2137.json
   ```
