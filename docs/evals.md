# CareerMatch 评测

CareerMatch 的质量用两套数据衡量：

- **离线评测**：在固定评测集上跑匹配分析的各个版本，对比准确性、稳定性、
  成本和耗时。改动 prompt、模型或流程前后都跑一次，用数字判断改动是否有效。
- **线上指标**：每次 LLM 调用写一条记录，`/api/metrics` 统计真实使用中的
  成功率、耗时分位数和成本。

## 运行 CareerMatch 离线评测

在 `backend/` 下运行：

```bash
python -m evals.run                                       # v1/v2/v3 各跑 3 遍，带编造检测
python -m evals.run --versions v3 --runs 1 --jobs 3 --no-judge   # 快速冒烟
python -m evals.run --langsmith                           # 同时作为实验上传到 LangSmith
```

结果写到 `evals/results/eval_<时间>.json`（全部原始记录）和同名 `.md`
（汇总表）。完整跑一次三个版本约 5 分钟，花费约 0.5 美元，
其中裁判约 0.25 美元。

评测会调用真实 LLM、产生费用，所以不随 CI 自动运行。GitHub Actions 里的
**Eval** workflow 可以手动触发，需要先在仓库 Secrets 里配置 `DEEPSEEK_API_KEY`。

评测期间不写线上指标表；不加 `--langsmith` 时也会关掉链路追踪，
避免评测流量混进线上数据。

## CareerMatch 评测集

评测集在 `backend/evals/dataset/`，由 `python -m evals.export_dataset`
从本地库导出：

- `jobs.json`：15 个真实岗位的结构化字段，与线上分析时传给模型的字段一致。
- `profile.json`：脱敏画像。仓库公开，姓名、学校、公司名换成占位符，
  技能、项目、学历层次和求职意向保留。
- `labels.json`：差距标注，每个岗位标出候选人真正缺的技能及其常见说法。

> [!IMPORTANT]
> `labels.json` 目前是规则生成的草稿，15 个岗位都还没有人工校对
> （`reviewed: false`），所以差距识别的准确率和召回率暂时为空。
> 校对方法见文末。

## CareerMatch 评测指标

- **成功率**：分析成功返回的比例。
- **耗时 P50 / P95**：单次分析的端到端耗时，只统计成功的。
- **token 与成本**：一次分析里所有 LLM 调用的 token 之和。成本按
  `app/core/config.py` 的价格表估算，取 DeepSeek 官方高峰时段价格，偏保守。
- **分数算错次数**：`match_score` 与四个子分按权重算出的值不一致的次数。
- **空泛建议**：行动建议命中「系统学习」「刷LeetCode」等短语的条数，
  口径与 v1→v3 的历史评测一致。
- **稳定性**：同一岗位跑 3 遍，看分数的标准差、最大极差和完全一致的比例。
- **差距识别准确率 / 召回率**：模型给出的缺失技能与人工标注比对，
  任一别名出现在任一条预测里（不区分大小写）就算识别到。
- **编造率**：用更强的 `deepseek-v4-pro` 当裁判，逐条检查建议有没有把画像里
  不存在的经历、项目、技能说成候选人已有的。「建议去做」不算编造。

裁判本身也做过校验：构造一条明显编造的建议（画像里没有的实习和 Kafka 经验）、
一条引用真实项目的建议、一条「去学」的建议，裁判全部判对。

## CareerMatch 各版本对比

2026-10-09，模型 `deepseek-flash`，15 个岗位 × 3 次，
原始记录见 `evals/results/eval_20261009_2137.json`。

| 指标                        | v1 单 prompt | v2 两步链 | v3 LangGraph |
| --------------------------- | ------------ | --------- | ------------ |
| 成功率                      | 100%         | 100%      | 100%         |
| 耗时 P50                    | 6.3s         | 10.6s     | 10.0s        |
| 单次成本（美元）            | 0.0016       | 0.0027    | 0.0020       |
| 分数算错                    | 28 / 45      | 0 / 45    | 0 / 45       |
| 空泛建议                    | 6 / 135      | 0 / 135   | 0 / 81       |
| 分数标准差                  | 0.46         | 0.55      | 0.41         |
| 3 次分数完全一致的岗位比例  | 53%          | 60%       | 80%          |
| 编造率                      | 0%           | 0%        | 0%           |

- **让 LLM 自己做加权求和不可靠**：v1 有 62% 的结果分数算错，偏差 1 到 2 分。
  v2 起改为代码里按子分加权，错误归零。
- **拆成两步后建议质量更好**：v1 有 6 条空泛建议，v2、v3 为 0。
- **v3 比 v2 便宜约 26%**：技术栈不符的岗位由规则节点直接跳过建议生成，
  省掉一次 LLM 调用。
- **temperature 为 0 仍有波动**：同一岗位多次分析，分数最大相差 9 分。
- **编造率在当前评测集上没有区分度**：三个版本都是 0。这个指标保留下来，
  用于后续加自检节点、换模型时做回归检测。

## 评测驱动的修复：规则筛选误排除

上面的结果里，v3 只给 15 个岗位中的 9 个生成了建议。排查发现规则筛选只要
在必需技能里看到 Java 或 Golang 就排除岗位，但其中两条要求其实是多选一：
`Python/Java/Scala` 和 `至少一种编程语言（如Java、Python等）`。
被误排除的恰好是「大模型应用开发工程师」和「AI应用开发工程师」两个目标岗位，
它们完全拿不到提升建议。

修复：命中排除语言的那条要求里，如果同时列了候选人已有的技能，视为多选一，
不排除；技能按完整单词比对，避免 `SQL` 命中 `MySQL`。真实 JD 里的这几种
写法都加进了单元测试。修复后重跑 v3（`eval_20261009_2140.json`）：

| 指标                  | 修复前 | 修复后  |
| --------------------- | ------ | ------- |
| 被排除的岗位          | 6      | 4       |
| 其中误排除            | 2      | 0       |
| 单次成本（美元）      | 0.0020 | 0.0023  |
| 空泛建议              | 0 / 81 | 0 / 99  |
| 编造率                | 0%     | 0%      |

成本上升约 13%，是因为多给两个岗位生成了建议，属于预期内的代价。

## 与 2026 年 7 月历史数据的关系

README 早期的 v1→v3 对比（v1 算错 7/15 等）是 7 月在 `deepseek-chat`
上用旧脚本跑的。`deepseek-chat` 已是弃用别名，现在实际由 `deepseek-flash`
响应。本文数据换了模型、画像改为脱敏版本、每个岗位跑 3 遍，
两批数字不能直接比较，结论方向一致。旧脚本（`evals/*_eval.py`）保留，
用于复现当时的结果。

## CareerMatch 线上指标

```bash
curl https://<你的域名>/api/metrics?days=7
```

返回总体和按角色（analysis、suggest、jd_parse、agent 等）分组的调用次数、
成功率、耗时 P50/P95、平均 token 和估算成本，以及平均单次匹配分析成本。
数据来自 `llm_calls` 表，每次 LLM 调用写一条，写入失败不影响请求本身。

## CareerMatch 评测的已知局限

- 评测集只有 15 个岗位、一份画像，结论适合版本间相对比较，不代表通用水平。
- 编造率依赖 LLM 裁判，可能有误判；校验只覆盖了少量构造样本。
- 成本按高峰价估算，DeepSeek 非高峰时段半价，实际花费更低。

## 校对 CareerMatch 差距标注

1. 打开 `backend/evals/dataset/labels.json`，每个岗位的 `missing` 是规则草稿：
   JD 必需技能里画像没覆盖的项。规则很粗，比如会把画像已有的
   「DeepSeek API」对应的「LLM API」误判为缺失。
2. 对照 `jd_required` 和画像，删掉不算缺失的、补上漏掉的。
   `aliases` 写上模型可能用到的说法，例如 `["RAG", "检索增强"]`。
3. 改完一个岗位就把它的 `reviewed` 改成 `true`，只有校对过的岗位参与计算。
4. 不用重跑 LLM，直接用已有结果重新计算：

   ```bash
   python -m evals.rescore evals/results/eval_20261009_2137.json
   ```
